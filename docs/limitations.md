# Limitations

- **Scope.** TypeScript on Node with Vitest and StrykerJS. The demo domain is deliberately small; budgets cap an MR at 5 files, 100 changed lines and 64 mutants per run.
- **A survivor is not a bug.** It shows a behaviour change no test detects. Equivalent mutants (changes no input can observe) exist; the model may label one `equivalent`, which is reported but never changes the score.
- **Arid triage is heuristic.** It removes logging, error-message text and log-only blocks. It can miss other noise and, rarely, hide a mutant on a line that also logs.
- **Draft execution.** AI-drafted tests run in child processes with credentials stripped from the environment, inside the Duo sandbox, after static guardrails (no mocks, no environment, network or dynamic imports). The guardrails are defence in depth, not a sandbox of their own.
- **Same-repository evaluator.** An MR can edit its own CI and evaluator. Changes to protected paths make the gate inconclusive rather than passing, but hostile-repository use needs a policy evaluated from a protected source (for example a compliance pipeline).
- **Role checks in the flow.** The flow's `ai_workflows` token may be refused by GitLab's users and members APIs. Then `apply` fails closed unless GitLab reports this run's own effective permission (the triggering person's composite identity) as Developer or higher and the command is the comment that started the run. Overrides are always verified by the CI gate with its own token.
- **Commit race.** Approved tests are committed to the MR branch with per-file last-commit guards and a head check right before the write. GitLab has no branch-wide compare-and-swap, so a push in the same second could interleave; the next pipeline re-evaluates the gate either way.
- **Token accounting.** GitLab doesn't expose model tokens per flow run. What is measured is the prompt text itself: Mutant Review builds the per-finding drafting context for the findings it sends (at most three) and for every surviving mutant, and reports the characters triage kept out. The token figure is that count divided by four, a rule of thumb, and is always labelled approximate. Shared preamble, requirement docs and test-file excerpts are excluded from both sides. No money or inference-energy figure is derived from it.
- **Footprint.** The SCI receipt uses published power coefficients (not a wattmeter), Google's annual location-based grid average (SCI prefers marginal rates, which are not published for these regions), and a boundary that excludes job setup, network, storage and model inference. CPU time is measured on Linux only; elsewhere full load is assumed and flagged. Per-MR whole-file costs are projections from the whole-file dry run plus the measured cost per mutant; only `benchmarks/energy.ts` executes both arms. The whole-file dry run that measures the saving is itself part of the footprint; it is skipped when the changed lines already cover every candidate line of their files (the demo, new files), judged by the same line classifier that builds the scope, so a mutation site on a line it treats as non-executable would be missed by the count. See [sustainability.md](sustainability.md).
- **Pre-push check.** `mutation_check` uses the project's Stryker and Vitest configuration, so it covers what that configuration tests (in this repository, the demo domain). It runs Stryker on the developer's machine with the same budgets as CI, and `verify_test` temporarily writes the draft into the test file and restores it.
- **Lost protection.** Only existing test files that the Stryker test run includes (`vitest list` on the target branch) and the production TypeScript they import by relative path are considered. Test helpers, fixtures, setup files and path-alias or package imports are not followed. Protection is measured with Stryker's mutators, so a loosened assertion that still kills every mutant Stryker generates is not reported (Stryker does not mutate numeric literals: changing an expected amount from 500 to 700 is invisible to it). Mutants on lines the MR also changed go to the changed-line review instead. The target-branch run mutates the whole imported files, bounded by the policy's file and runtime budgets; an over-budget or unfinished check makes the gate inconclusive. Both runs use the MR head's Stryker configuration, which is a protected path. The demo's second scenario (a loosened exact-$100 test) runs in a scratch repository and is shown in Front Desk, never gated.
- **Live status.** See the Status table in the README for what has run on GitLab versus in automated tests.
- **Benchmark.** One run on Windows, survivors not human-reviewed, and Stryker 10 generates no mutants inside TypeScript `as` expressions, so 5 of the 25 PRs had none. Details in `benchmarks/RESULTS.md`.
